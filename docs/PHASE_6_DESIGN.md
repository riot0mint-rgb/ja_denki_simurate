# フェーズ6 設計（改訂版）：料金改定レビュー

**改訂日**: 2026-08-20
**改訂理由**: フェーズ1〜4の実装により、料金の取得が確定した
**旧設計**: 管理画面（Webフォームで料金を編集し、承認ボタンで反映）＋ 料金自動取得ボット

---

## 1. なぜ設計を変えたか

当初のフェーズ6は「単価がどこから来るか分からない」ことを前提にしていた。
だから **管理画面で人が数値を打ち込み、承認ボタンで反映する** 設計になっていた。

フェーズ1〜4で前提が変わった。

| 当初の想定 | 実際に判明したこと |
|---|---|
| 単価の在処が不明 | JAでんき公式試算表（①〜⑥・au）に全プランが揃っている |
| 計算ロジックが不明 | 8構造すべてを Excel の数式から解読・実装済み |
| 抽出が人手頼み | セル番地単位で機械的に取り出せる |
| 検算手段がない | 早見表1201点の回帰テストがある |
| 改定の入手経路が不明 | 適用月ごとに新しい試算表が Google Drive に置かれる |

**単価は「人が打ち込むもの」ではなく「元資料から取り出すもの」になった。**
そうすると管理画面のフォームは、正確に写された値をもう一度手で打ち直させる装置でしかない。
打ち直しは転記ミスを増やすだけで、精度は上がらない。

もう一点。旧設計は承認記録を独自に持つ想定だった（監査ログテーブル）。
しかし CLAUDE.md はすでに **「削除・強制プッシュは厳禁（ログ消失で対応不可に）」**
「ロールバックは `git revert`」と定めている。承認の記録媒体は Git がふさわしい。

---

## 2. 新しい設計

**フェーズ6は画面ではなくパイプラインにする。**
承認は Pull Request のレビューで行い、監査証跡は Git の履歴とする。

```
新しい試算表（Google Drive）
        │
        │ ① 取り込み           npm run rate-intake -- <xlsx...>
        ▼
   rates.ts の改定案（ブランチ）
        │
        │ ② 検証               npm test / npm run rate-master:check
        ▼
   料金マスターの再生成
        │
        │ ③ 差分レポート        npm run rate-master:diff
        ▼
   Pull Request（差分レポートを本文に）
        │
        │ ④ 人の承認 ★ここだけが人の仕事
        ▼
   main へ merge → 本番デプロイ
        │
        │ ⑤ 利用者へ            Service Worker の更新バナー
        ▼
   「新しい料金データがあります／更新する」
```

### 人がやること／機械がやること

| 工程 | 担当 | 根拠 |
|---|---|---|
| 元資料からの抽出 | 機械 | 人の転記はミスを増やす |
| 計算構造の判定 | 機械 | Excel の数式が正 |
| **単価と出典の対応の確認** | **人** | ルール4 |
| **改定を本番に出す判断** | **人** | ルール10 |
| 検算 | 機械 | 1201点の回帰テスト |
| 記録 | Git | ルール「削除・強制プッシュ厳禁」 |

## 3. 実装状況

### ✅ 完了

**`scripts/generate-rate-master.ts`** — 正本（`rates.ts` / `monthlyRates.ts`）から
`data/rate_master.json` を生成する。金額は文字列で書き出す（JSON の number にすると
浮動小数に戻るため。ルール2）。CI が `--check` で drift を落とす。

**`scripts/rateMasterDiff.ts` / `scripts/rate-master-diff.ts`** — 改定前後の差分を
PR にそのまま貼れる Markdown で出す。承認者が読むのは JSON の行差分ではなく
「どの値が、いくらから、いくらに、どの出典で変わったか」。

出力例:

```markdown
> ⚠️ 出典が据え置きのまま単価が動いています。転記ミスでないか確認してください。
>
> - JAでんき 従量電灯A（`ja_denki_juryo_a`）

#### 変更: JAでんき 従量電灯A (`ja_denki_juryo_a`)

| 項目 | 変更前 | 変更後 |
|---|---|---|
| `tiers[0].unitPriceYenPerKwh` | 32.22 | 33 |

出典:
- ①JAでんき試算表(...)26年7月適用.xlsx 基本項目!E26:E29（規制料金）
```

**出典の据え置き検知**が肝。単価が動いたのに `sources` が変わっていないのは、
新しい元資料を見ずに数字だけ書き換えた疑いがある。転記ミスの主要な形なので機械が指摘する。

**回帰テストによる関門** — 実際に JA従量電灯A の第1段階を 32.22 → 33.00 に
書き換えて確かめたところ、`217kWh 付近で推奨プランが従量Sから従量Aへ入れ替わる`
が落ちた。**根拠のない単価変更はテストを通らない。**

### ⏳ 未実装

**`scripts/rate-intake.ts`** — 新しい試算表 xlsx を読み、`rates.ts` の改定案を出す。

現状は Excel の解読を対話的に行っている。これを再実行可能な形にする。

- 入力: `シミュレーション【YY年M月適用】/` 配下の xlsx 一式
- 出力: `rates.ts` の差し替え案 ＋ `monthlyRates.ts` への月次行の追記
- セル番地は現行の `RateSource.locator` をそのまま使う。番地が動いていたら
  **推測せず落とす**（ルール8）。書式が変わったなら人が読むべき場面である
- Node には Excel パーサが要る。`exceljs` を想定（`openpyxl` で解読した経緯があるため
  Python 版でもよいが、CI と揃えるなら Node が扱いやすい）

**GitHub Actions での改定PR自動作成** — 上記が動いてから。
Drive の監視まで自動化するかは、改定が年数回であることを踏まえると費用対効果が薄い。
まずは手元で `npm run rate-intake` を叩ければ十分。

## 4. 旧フェーズ7（料金自動取得ボット）の扱い

**縮小する。**

旧設計は各社サイトのスクレイピングを想定していた（`SCRAPING_POLICY.md`）。
しかし本プロジェクトが比較しているのは **JAでんきが自ら作った試算表** であり、
これは Google Drive 経由で確実に入手できる。スクレイピングで各社サイトから
取り直す必要はない。

さらに実務上の裏付けがある。フェーズ1で判明したとおり、
**同じプランでも試算表ごとにモデル化が食い違う**（夜トクの基本料金半額の扱い、
JA従量電灯A 最低料金の 759.68 と 759.67 など）。
各社サイトの表記を機械的に取り込むと、この食い違いを解決できないまま値が入る。
「そのプラン専用の試算表を正とする」という現在の判断は、人が元資料を比べたから下せた。

したがってスクレイピングは **裏取り（cross-check）専用** に位置づけ直す。
値の反映元にはしない。`SCRAPING_POLICY.md` の「人間承認プロセス」は
本設計の PR レビューに読み替える。

## 5. この設計で満たせる CLAUDE.md のルール

| ルール | 満たし方 |
|---|---|
| 1. 料金計算に LLM を使わない | パイプラインに生成AIは登場しない |
| 2. 金額に浮動小数を使わない | JSON でも金額は文字列。読み込み時に Decimal へ |
| 3. 元資料を変更しない | 試算表は読むだけ。書き込み先はリポジトリのみ |
| 4. 出典のない単価を登録しない | `RateSource` は型で必須。差分レポートが出典を必ず表示 |
| 5. 端数処理を省略しない | `RoundingProfile` はプランごとに必須項目 |
| 6. テストなしで料金ロジックを変更しない | 1201点の回帰が CI の関門 |
| 10. 自動で本番反映せず人が承認 | merge が承認。merge しない限り本番に出ない |
| ロールバック | `git revert`。強制プッシュは不要 |

## 6. 残る論点

**1. 改定の適用日と検針月のずれ**
料金は「◯月適用」で改定されるが、検針期間は月をまたぐ。現在は検針月で単価を引いており、
元資料の INDEX/MATCH と同じ挙動になっている。実務上これで正しいかは要確認。

**2. 過去月の単価をいつまで持つか**
`monthlyRates.ts` は 2025-01 以降を保持している。無制限に増えるので、
どこかで打ち切るか別ファイルに退避する判断が要る。

**3. 承認者の指定**
誰の approve をもって承認とするかは運用の取り決め。
GitHub の CODEOWNERS で `apps/web/src/data/rates.ts` と
`packages/calc-core/src/monthlyRates.ts` にレビュー必須を掛けるのが素直。
