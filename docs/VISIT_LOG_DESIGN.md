## なぜ、このアプリに訪問履歴を持たせないのか

### 1. このアプリは認証をかけていない

配布の前提が「URLを知っている職員が使えること」なので、**認証をかけていません**
（フェーズ9・SECURITY.md）。URLを知っていれば誰でも開けます。

いまはそれで問題ありません。**中に何も入っていないから**です。
訪問先の住所や氏名が入った瞬間、同じURLが「誰でも開ける顧客名簿」になります。
これは設計の欠陥ではなく、**前提と機能の組み合わせが破綻する**という話です。

認証をかければ解決しますが、それは配布の前提そのものを変えることになります
（「アクセス制限にかかりやすい実装を避けたい」というご要望と正面から衝突します）。

### 2. ハッシュ化は解決策になりません

「住所をハッシュ化すれば個人情報ではなくなるのでは」という案は、よく出ますが**誤りです。**

- ハッシュ化は**仮名化**であって匿名化ではありません。元の住所リストや対応表を
  組織が持っている限り、容易に照合できるため個人情報として扱う必要があります
- 住所の取りうる値は限られているので、**総当たりで元に戻せます**
  （「◯◯町1-2-3」を片端からハッシュ化して突き合わせるだけ）。
  ソルトを付けても、そのソルトが配布物の中にあれば意味がありません
- そして静的サイトに置くソルトは、**配ったページから誰でも読めます**
  （フェーズ8で生成AIのAPIキーを置けないと判断したのと同じ理由）

漏えい時の影響は多少減りますが、**法的な扱いも運用上の責任も変わりません。**
ここを誤解したまま作ると事故になります。

### 3. JAは既に組合員の名簿を持っています

重複営業を避けるのに必要なのは「この世帯にはもう行った」という情報で、
それは**組合員番号に紐づけるのが正しい**です。JAには既にその仕組みがあります。

このアプリの外に同じものを作ると、

- 名簿が二重になり、どちらが正かが分からなくなる
- 開示・訂正・利用停止の請求に、二か所で応える必要が出る
- 保存期間・安全管理措置を、二か所で担保する必要が出る

**作らないことが、いちばん安全で、いちばん安く済みます。**

## いま実装したもの — 個人にたどり着けない商談ログ

商談ナビの「ふりかえり」で、その商談の記録を1行で書き出せます。

### 書き出す列

| 列 | 例 | なぜこの粒度か |
|---|---|---|
| 日付 | 2026-08-22 | **時刻は持たない。** 時刻＋地域は絞り込みの手がかりになる |
| 到達段階 | closing | どこで止まったかの分析用 |
| 温度感・世帯・日中在宅・オール電化・気がかり | curious / small … | ヒアリングの区分。人数などは区分のみ |
| 現在の契約 | chugoku_juryo_a | プラン別の傾向 |
| 使用量帯 | 300〜500kWh | **実数は持たない。** 実数だと「この地区でひと月◯◯kWhの世帯」が一意に決まりうる |
| 年間差額帯 | 3千〜1万円 | いくら安くなると決まるのかを見る軸 |
| 出た反論 | think;no_need | 台本を厚くする箇所を決める |
| 結果 | applied | 申込率 |

**氏名・住所・電話・お客様番号・供給地点特定番号の列は、そもそも作れません。**
`assertNoIdentifyingColumn` が書き出しのたびに検査し、それらしい列名があれば落ちます
（`visitLog.test.ts` で固定）。

### 端末に保存しません

書き出した内容は画面に出るだけで、`localStorage` にも `IndexedDB` にも入れません。
画面を閉じれば消えます。この性質は CI の関門（`npm run security:check`）で守られています。

タブレットを複数の職員で共有することがあるため、**前の人の商談が次の人に見えない**
という性質は、そのまま個人情報保護の担保にもなっています。

### 組織へ集める導線

```
職員の端末            支店・本店
┌──────────────┐     ┌──────────────────────────┐
│ 商談ナビ      │     │ 既存の集計表             │
│  ↓ 1行をコピー │────→│（Excel / グループウェア）│
│  （保存しない）│     │  支店・担当の列は組織側で足す │
└──────────────┘     └──────────────────────────┘
                            │ 全体を貼り戻す
                            ↓
                     ┌──────────────────────────┐
                     │ 「営業の集計」画面        │
                     │  その場で数えるだけ       │
                     │ （保存も送信もしない）    │
                     └──────────────────────────┘
```

集計画面は**見出しの名前で列を読む**ので、組織側が「支店」「担当」「訪問日」などの
列を足しても、順番を入れ替えても動きます。現場の表は必ず育つので、位置で読んではいけません。

### 何が分かるか

- **いくら安くなると決まるのか**（年間差額帯ごとの申込率）— 訪問先の選び方が変わります
- どの段階で止まっているか — 台本の弱いところが分かります
- どの反論が多いか — 台本を厚くする場所が決まります
- お客様の気がかり別・現在の契約別の傾向

母数が5件に満たない区分では割合を出しません。1件2件の割合は判断を誤らせるためです。

## 重複営業の回避 — 実装するならこう（未実装）

**このアプリではなく、JAの既存の仕組みに置いてください。**

### 置き場所と識別子

| 項目 | 案 |
|---|---|
| 置き場所 | 組合員管理システム、またはJAが既に使っているグループウェア |
| 識別子 | **組合員番号**（JAが既に持っている）。住所やそのハッシュではなく |
| このアプリの役割 | 商談ログの1行を出すところまで。番号の入力欄は作らない |
| 紐づけ | 職員が集計表に貼るときに、組織側で組合員番号の列を足す |

この形なら、アプリ側は最後まで個人情報を1バイトも扱いません。
組合員番号と商談ログが結びつくのは、**認証のかかった組織のシステムの中だけ**です。

### 着手前に整えるもの

個人データの取り扱いになるため、実装より先に次が要ります。

- [ ] 利用目的の特定と、組合員への通知または公表
  （「訪問営業の重複を避けるため」を利用目的に含めてよいかの確認）
- [ ] 安全管理措置（アクセス制御・記録・持ち出しの制限）
- [ ] 従業者の監督（誰が見られるか）
- [ ] 保存期間と、期間を過ぎた記録の消し方
- [ ] 開示・訂正・利用停止の請求への対応手順
- [ ] 「訪問を断られた」記録の扱い（お断りの意思は、より慎重な扱いが要ります）

⚠️ **具体的な法令上の要件は、JAの法務・コンプライアンス担当にご確認ください。**
この文書は設計の見取り図であって、法的な助言ではありません。

### 運用でできる暫定策（システム改修なし）

すぐ効いて、リスクが増えない方法もあります。

1. **訪問先リストを配る側で重複を潰す。** 支店で訪問先を割り当てるときに、
   既存の名簿に「訪問済み」の印を付けて回す。アプリは関与しない
2. **お断りリストを最優先で共有する。** 「訪問しないでほしい」と言われた先を
   もう一度訪ねるのが、いちばん信用を落とします。
   重複営業の回避で本当に効くのはここで、これは既存の名簿でできます

**まず 2 だけでも運用に載せる価値があります。**

## 段階の提案

| 段階 | 中身 | 前提 |
|---|---|---|
| **1（実装済み）** | 個人にたどり着けない商談ログ＋集計 | なし。今日から使えます |
| **2** | お断りリストの運用（既存の名簿に印を付ける） | 運用のみ。システム改修なし |
| **3** | 訪問済みフラグを組合員管理に持つ | 上記チェックリスト、既存システムの改修 |
| **4** | 商談ログと組合員番号の紐づけ | 段階3が動いてから。アプリ側の改修は不要 |

段階1の集計が溜まると、**そもそもどの世帯を訪問すべきか**が数字で分かります。
重複を避ける前に、訪問先の選び方のほうが効くかもしれません。
