# 受け入れテスト手順書 (ACCEPTANCE_TEST.md)

**対象**: JAでんき料金比較シミュレータ（Phase A）
**目的**: 本番に出してよいかを、担当者が自分の目で確かめる
**最終更新**: 2026-08-21（フェーズ9）

---

> **手早く動作を見たいだけなら [SMOKE_TEST.md](./SMOKE_TEST.md)（15〜20分・検針票不要）**
> をどうぞ。決まった数字を入れて決まった数字が出るかを確かめるだけのシートです。
> こちらは**本番に出してよいかを決める**ための手順書です。

## この文書の使い方

2部構成です。

| | 誰が | 所要 | 中身 |
|---|---|---|---|
| **第1部** | 開発担当 | 約5分 | コマンドを打つだけ。13項目を機械が確かめる |
| **第2部** | 業務担当（営業・料金担当） | 約30分 | 機械には判断できないことを人が見る |

**第1部が全部通っていない状態で第2部に進まないでください。** 手戻りになります。

# 第1部 機械による確認（開発担当）

```bash
# 準備（初回のみ）
npm ci
npm install --no-save playwright

# 1. すべてのテスト（817件）とカバレッジの閾値
npm run test:coverage

# 2. 型
npm run type-check

# 3. 料金マスターJSONが正本とずれていないか
npm run rate-master:check

# 4. 元資料（archive/ に試算表がある場合）との突合
npm run rate-intake

# 5. ビルド
npm run build

# 6. 端末の外に出る経路が無いこと（静的）
npm run security:check

# 7. 本番依存の脆弱性
npm audit --omit=dev --audit-level=low

# 8. 端末の外に出ていないこと（実機）
npm run security:runtime

# 9. 受け入れテスト（実機・55項目）
npm run accept
```

1〜7 は CI でも毎回走ります。**8・9 はリリース前に手元で1回**走らせてください
（ブラウザの取得が重いため CI には入れていません）。

# 第2部 人による確認（業務担当）

機械が確かめられるのは「そう書いてある」までです。
**その数字を営業の場で出してよいか**は人にしか判断できません。

## 準備

配布された URL を**スマートフォンで**開いてください。
営業の場で使うのはスマートフォンです。PCだけで確認すると見落とします。

---

## 2-1. 検針票と突き合わせる（いちばん重要）

**ご自身か、ご家族の実際の検針票を1枚ご用意ください。**

1. 「検針票から試算する」を押す
2. 検針票の「ご契約種別」と同じプランを選ぶ
3. 検針票の検針月を選ぶ
4. 検針票の「ご使用量（kWh）」を入れる
5. 「詳しい結果を見る」

**確認**:

- [ ] 「料金比較表（月額）」の**現在のプランの金額**が、検針票の請求額とほぼ一致するか
- [ ] ずれている場合、何円ずれているか記録する

> 数十円のずれは正常です。検針票発行手数料（1契約55円）やポイント還元を
> 含めていないためです。**数百円以上ずれる場合は報告してください。**

ずれた場合に書いていただきたいこと: 契約種別 / 検針月 / ご使用量 / 検針票の請求額 / 画面の金額

---

## 2-2. 説明できる言葉になっているか

結果画面を、**お客様に説明するつもりで**読んでください。

- [ ] 「年間の想定おトク額」の意味を、お客様に一言で説明できるか
- [ ] 「1年ぶんの見積もり方」の2つの違いを説明できるか
- [ ] 「差が出ている理由」に書いてある文章は、そのまま読み上げて通じるか
- [ ] 分かりにくい／固い／誤解を招く表現があれば書き出す

### 特に見ていただきたい文言

| 場所 | いまの文言 |

## 2-3. 安くならないケースを見る

「auでんき Mプラン」を選び、検針月を **2026年7月**、ご使用量 **348kWh** で試算してください。

- [ ] 「年間の想定**ご負担増**額」と赤系の色で出るか
- [ ] この画面を営業の場で出してよいか
- [ ] 出さないほうがよい場合、どう振る舞うべきか（非表示／別の言い方／担当に相談を促す）

同じく「中国電力 ナイトホリデー」を、ナイトタイムのみ **300kWh**・6kW で試算してください。

- [ ] 高く出ることが分かるか（442kWh未満では必ず高くなります）

> **これらは計算誤りではありません。** 元資料と方向が一致しています。
> 「安くならないお客様に、安くならないと伝える」ことの是非をご判断ください。

## 2-4. 1年ぶんの見積もり方

**夏か冬の検針票**で試算し、「毎月おなじ」と「季節で変わる」を押し比べてください。

- [ ] おトク額が変わることに気づけるか
- [ ] どちらを既定にすべきか（いまは「毎月おなじ」）
- [ ] お客様に見せるとき、どちらで説明したいか

> 8月に348kWhのお客様の場合、毎月おなじ＝年4,176kWh／おトク5,231円、
> 季節で変わる＝年3,482kWh／おトク3,826円。**1,400円ほど変わります。**

## 2-7. 商談ナビの確度と、次の訪問の決め方（営業経験のある方に）

商談ナビを最後（振返）まで進めてください。

- [ ] 確度 A〜E の分かれ目が、現場の感覚と合っているか
- [ ] 「起きたことを控える」の項目が、実際にその場で答えられるものか
- [ ] 「次に行くのは」の間隔（A=約束の日 / B=1〜2週間 / C=口実ができたとき）が妥当か
- [ ] 「次に行くときの口実」を、そのまま口に出せるか
- [ ] 高くなる結果のとき、追いかけない判断で良いか

> **確度の重みは仮説です。** いまは「次回の約束＋3、検針票を見せていただけた＋2、
> 解約金の質問＋2、感触±1」で計算しています。感触を軽くしているのは、
> 素人の感触が当てにならないためですが、**±1 が軽すぎるなら教えてください。**
> 集計画面の「確度の判定は当たっているか」で、後から実績と突き合わせて直せます。

- [ ] 「今後の訪問はご遠慮したい」を選んだとき、名簿への反映手順が支店に周知されているか
      （手順書: docs/VISIT_REFUSAL_PROCEDURE.md。
      **アプリは画面に出すところまでです。反映は人がやります**）
